# 手动触发更新与自动保护

## 实际流程

已按用户要求取消每小时定时检查，workflow 不再含 schedule。

日常流程：进入反代面板 → 原有作者更新检测/提醒 → 用户点击“立即更新” → 受保护 /api/deploy → 独立检查器备份、发布、八项关键检查 → 成功保留新版本，异常回滚。只检查更新不会发布。独立检查器的每分钟 Cron 保留，用于已提交任务的检查和恢复，不检查作者版本、不发起新升级。

面板按钮沿用现有多模块更新入口，保留线上定制功能；它不启动 GitHub CI，不自动同步 fork。下述 GitHub 整合、完整测试、发布及分支同步流程，作为额外的维护工具保留，仅在 CLI 明确运行 workflow_dispatch 时执行；不在打开面板时执行。

### 手动 GitHub 维护流程

1. 从作者 `main` 获取最新提交，与 `custom/upstream.lock.json` 比较；没有变化时仅检查线上基准和独立保护器是否就绪，不重复发布。
2. 核对作者历史、版本不降级、自动化边界；作者修改 `custom/`、`.github/`、`.gitignore` 或 `.gitmodules` 时停止，交人工适配。
3. 在临时整合分支合并作者代码、更新版本锁，执行完整 `npm test` 及公开树隐私检查。补丁结构变化、冲突或失败则不发布。
4. 在全新发布任务中，从**本次 workflow 原始可信提交**读取控制器，而非执行候选代码。确认维护分支未变化、线上适配器指纹与启用时基准一致、没有未完成更新/恢复。
5. 调用面板现有受保护 `/api/deploy`，不重试该 POST。独立检查器先备份当前源代码、版本、设置/绑定元数据及配置表，再发布候选，执行八项关键检查；失败则恢复原版本，Cron 在页面关闭或 GitHub 任务中断后仍继续处理。
6. 发布结果 `passed` 后，在另一个没有生产凭据的任务中核验 Git bundle、提交祖先、锁定文件、作者源码 SHA-256 和定制边界。使用原子普通快进推送，同时更新 fork 的纯作者 `main` 和 `codex/rex-custom`。拒绝强制覆盖。

作者提交只有说明更新、核心 SHA 未变时，测试和线上基准通过后同步仓库，不重复部署。自动更新只更换作者核心；测速、DNS 手动提交、Telegram、统计、多模块更新器和独立检查器保留线上现有版本。更新我们自己的定制代码仍走单独的备份与维护发布。

## 隔离与凭据

- 整合/测试任务没有生产凭据，GitHub Token 只读，checkout 不保存凭据。
- `production-automatic` 环境仅允许 `codex/rex-custom` 部署，保存三个加密 Secret：`REX_PANEL_ORIGIN`、`REX_PANEL_ADMIN`、`REX_EXPECTED_ADAPTER`。Secret 通过 CLI stdin 配置，不写进源码、日志或构建包。
- 面板管理员认证具有管理权限，只在可信发布任务运行期间提供；需要撤销自动发布时可先停用 workflow，再删除环境 Secret。该凭据不是 Cloudflare API Token。Cloudflare 编辑/DNS/Telegram Token 不交给 GitHub。
- 生产任务不安装依赖、不执行候选源码；候选 Worker 仅作为文本交给现有独立保护器。
- 分支发布任务只有本仓库写权限，没有生产 Secret。上游自动修改 workflow 的情况拒绝合并。
- 不修改 Surge，不自动选择正式 DNS，不向 Telegram 发测试消息。

## 失败记录与针对性修复

失败创建本仓库 Issue：`Automatic update blocked: <完整作者提交 SHA>`，附阶段与运行链接。后续发现相同 SHA 且该 Issue 仍打开时，暂停自动发布，不重复部署。新作者提交会重新进行完整检查。故障 Issue 是审计记录，仓库公开；不向其中粘贴节点、地址、Token、原始数据库或完整私有备份。

每次运行保存 `automatic-candidate`（公开候选源码、清单；验证通过时还含 Git bundle），保留 30 天。生产任务保存脱敏 `automatic-protection-report`（任务 ID、状态、版本、检查项通过情况），保留 90 天。真正代码与配置备份仍在 Cloudflare D1 的更新保护表；可在面板查看/下载私有故障报告，详见[更新保护与故障修复](更新保护与故障修复.md)。

| 阶段 | 定位/修复 |
| --- | --- |
| 作者历史/冲突/边界校验 | `automatic-integration.mjs`、Git 合并冲突；人工维护整合分支，保留双方改动 |
| 回源补丁不匹配 | `prepare-upstream.mjs` 和 `src/self-update.js` 的 `patchProxyFetch`，同步修复补丁并测试 |
| 定制功能测试失败 | 查看失败 test 脚本，修复对应定制模块；不要删除断言跳过兼容检查 |
| 线上基准/指纹不符 | 核对实际部署来源和变更；验证定制模块后再更新 `REX_EXPECTED_ADAPTER` Secret，禁止直接放宽检查 |
| 发布后检查不通过 | 面板更新保护记录和报告，确认已回滚/仍恢复中，再修复对应检查项映射的文件 |
| 分支发布失败 | 核对生产任务是否已 passed，维护分支是否被其它提交更新；重新整合健康线上版本，不盲目回滚健康服务或强推 |
| 请求超时/响应丢失 | 先核对面板任务 ID/最新更新记录及当前版本，防止重复提交；独立 Cron 仍会接续 |

自动检查覆盖关键接口/结构与配置一致性，不等于每条真实播放链路、每次浏览器带宽和 Telegram 私聊端到端验收。Cloudflare 版本回滚也不自动覆盖新产生的数据库数据；涉及不兼容数据库迁移时需针对快照人工修复。

## CLI 操作

```sh
# 手动检查（无需新版本，也可检查当前线上基准）
gh workflow run automatic-update.yml --repo zt001110/ProxyHub_Emby --ref codex/rex-custom
# 完整测试当前代码并 dry-run 验证仓库推送权限；没有上游更新时不部署
gh workflow run automatic-update.yml --repo zt001110/ProxyHub_Emby --ref codex/rex-custom -f validate_current=true
# 查看结果/失败日志
gh run list --repo zt001110/ProxyHub_Emby --workflow automatic-update.yml --limit 5
gh run view RUN_ID --repo zt001110/ProxyHub_Emby --log-failed
# 修复、测试并确认上次任务已终止/回滚后，明确允许重试被阻止的版本
gh workflow run automatic-update.yml --repo zt001110/ProxyHub_Emby --ref codex/rex-custom -f retry_blocked=true
# 停用/启用手动维护工具（启用后仍无定时任务）
gh workflow disable automatic-update.yml --repo zt001110/ProxyHub_Emby
gh workflow enable automatic-update.yml --repo zt001110/ProxyHub_Emby
```

`exercise_deployment=true` 仅用于显式维护演练：没有作者更新时，也将当前作者核心通过保护接口重新发布一次，真实验证备份/发布/检查链路。该选项不得在日常面板操作中设置；没有任何定时调度。回滚故障注入仅使用既有私有维护脚本，普通自动任务不做故障注入。

如果需要交给 Codex 修复，可直接发：

> 自动更新失败了，请检查 zt001110/ProxyHub_Emby 的 Protected upstream maintenance (manual) 运行和故障 Issue，先确认线上任务及回滚状态，再针对失败原因修复，保留定制功能和配置。完整测试通过后重新走受保护发布并核验，更新说明、关闭已解决 Issue。全程用 CLI/API，不用画面点击，不公开凭据或节点。

本机工作副本不会随云端自动改动。手动维护前，在没有本地修改时 `git pull --ff-only origin codex/rex-custom`，再 materialize 新的私有发布目录；不要用旧的本机核心覆盖云端最新版。
